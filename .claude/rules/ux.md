# 화면 흐름 · UX 규칙

## 화면 흐름 (5단계)

1. **예산 화면** — 슬라이더(연소득·현금) → 지도에 단지가 초록/노랑/회색으로 켜짐(리빌).
   단지 탭 시 인라인 상세. **부채는 여기서 안 묻는다** — "천장"만 보여준다.
2. **"가능한 매물목록 확인하기"** → 매물 목록(초록·노랑, 가격순).
3. 목록에서 하나 선택 → **팝업**(위 정부상품 / 아래 은행상품, 트레이드오프 한 줄씩).
4. **자격 조건 입력 → 가능한 상품 목록**(`Eligibility.jsx`). 질문이 순서대로 열리고,
   답에 따라 불필요한 질문은 건너뛴다. 마지막에 **자격 되는 상품을 전부 카드로** 보여준다
   (상품명·대략 한도·왜 가능한지). **부채 입력 전에 뜬다** — 이 목록 자체가 두 번째 리빌.
   은행탭은 아직 placeholder("곧 준비").
5. 카드 하나 선택 → **조종간**(`Strategy.jsx`).

## 전략 (Strategy) — 이 서비스 정체성이 가장 진한 화면

**대출을 '조회'해주는 게 아니라, 원하는 집에 닿도록 '레버'를 쥐여준다.**
그래서 한도는 고정 결과가 아니라 사용자가 당기면 실시간으로 반응하는 값이다.

위→아래:
1. **부채 입력** (`DetailInfo`) — '대충' 받은 잔액이 레버의 시작 위치. 확정 전에는 한도를 그리지 않는다.
2. **한도 + 게이지** — 고른 집의 필요 대출액이 고정 목표선. 지금 닿는 한도와 천장선(레버 끝)을
   같은 막대 위에 그린다. 기준선은 안 움직이고 레버가 움직인다.
3. **레버 2개** — 부채 레버(왼쪽 = 일부상환 가정) / 소득 레버(오른쪽 = 인정소득 상향 가정).
   소득 레버는 가정값이다. `incomeRules.js`의 20%·10% 차감은 **한도 숫자에 반영하지 않는다**(보류).

### 조종간이 지켜야 하는 정직함
- **레버는 자격도 움직인다.** 소득 레버를 올리면 소득상한을 넘어 상품이 **닫힐** 수 있다.
  그래서 소득 레버 최대는 그 경로의 소득상한에서 자른다.
  소득을 올리는 게 항상 유리하지 않다는 게 이 화면의 도메인 지식이다.
- **레버가 안 먹히는 구간을 숨기지 않는다.** 벽이 담보(LTV)나 경로 한도면 부채·소득으로는
  안 내려간다. 그럴 때 `leversInert`로 잡아 "이 경로에선 레버가 결과를 못 움직여요"를 먼저 말하고
  열려 있는 길(현금 차액 / 다른 경로)로 넘긴다. **움직이는 척하면 거짓 희망 기계가 된다.**
- **보유 현금은 조종간에서 다시 묻지 않는다.** 부족분은 "차액 약 X를 현금으로 채우면 돼요"로만 번역한다.

### 레버 → 결과 파이프
```
DetailInfo(대충 입력) → base(레버 시작 위치) → pull(당긴 값) → lever
   lever ─→ products/limit.js  limitAt(productKey, lever, capOverride) ─→ { limit, parts, binding }
                               ceilingAt(...)                          ─→ 게이지의 천장선
   lever.income ─→ engine.withAssumedIncome(ctx) → deriveFacts → judgeAll ─→ 자격 재판정(다른 열린 길)
```
Strategy는 **어떤 상품인지 몰라도 된다** — `productKey`와 레버 값만 넘긴다.
상품 고유 지식(DTI냐 DSR이냐, 부채를 이자만 보는가 원리금으로 보는가)은 두 곳에만 있다 —
`PRODUCTS[key].capacityModel`(잣대 선택)과 `products/limit.js`의 `DEBT_VIEW`(DSR 계열의 부채 해석).
`limitAt`은 레버의 **raw 부채값**을 그대로 넘기고, 해석은 잣대가 한다.

## 질문을 늘리지 않는다

- **부채는 '잔액' 하나만 받는다.** 월상환액·만기를 쪼개 묻지 않는다 —
  DTI는 잔액의 이자만 보고(월 얼마씩 갚는지는 계산에 안 들어간다), DSR도 같은 잔액에서 원리금을 환산한다.
  질문을 늘리면 사용자는 멈추는데, 그렇게 받은 값이 계산에 쓰이지도 않는다.
- **세대주 여부를 직접 묻지 않는다.** 가족정보(나이·배우자·자녀)에서 추정하고, 결과에 노랑을 붙인다.
- 새 입력이 필요해지면 **그 경로에서만** 늘린다. 안 쓰는 질문을 다른 화면에 되살리지 말 것.

## 화면 경계 원칙 (이걸 어기면 예전의 중복으로 되돌아간다)

- **자격은 `Eligibility` 한 곳에서만 받는다.** Strategy·products는 자격을 다시 묻지 않는다.
  자격 질문이 더 필요해지면 `EMPTY_ELIG`에 필드를 추가하고 Eligibility에 UI를 단다.
- **부채는 `DetailInfo` 한 곳에서만 받는다.** 자격 화면에는 절대 올리지 않는다
  — 자격은 소득상한 위/아래로 갈리지 부채로 갈리지 않기 때문.
- **소득 신뢰도(초록/노랑)는 `IncomeCheck` 한 곳.** 한도 숫자는 안 깎는다.
- 한 번 받은 값은 화면을 오가도 다시 묻지 않는다(`person` 한 벌).

## 색의 뜻 (가드레일 3·4)

- **초록** = 예산 안. **노랑** = 경계선 또는 **상담역이 확정할 영역**. **회색** = 지금은 예산 초과.
- 노랑은 거절이 아니다. 회색·닫힘에도 "이렇게 하면 열려요" 경로를 같이 준다.
